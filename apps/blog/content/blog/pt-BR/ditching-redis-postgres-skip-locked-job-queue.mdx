_Tirar trabalho da requisição HTTP costuma disparar um reflexo: subir o Redis. No Alexandryn, uma tabela no PostgreSQL e o FOR UPDATE SKIP LOCKED garantiram jobs atômicos, zero escritas duplas e fencing por heartbeat sem nenhum daemon extra._

---

O PostgreSQL consegue operar uma fila de jobs em segundo plano extremamente confiável. O segredo é uma única cláusula: `FOR UPDATE SKIP LOCKED`.

Uma tabela, um punhado de consultas curtas e zero message brokers para instalar, monitorar ou gerenciar daemons.

Tirar trabalho pesado do caminho da requisição HTTP geralmente começa com uma dúvida batida: você precisa de Redis com Celery, Sidekiq, BullMQ ou RabbitMQ?

Se a sua aplicação já usa PostgreSQL, a resposta quase sempre é não.

Para o processamento assíncrono que a maioria das aplicações de fato precisa.. gerar relatórios, processar arquivos enviados, disparar webhooks, extrair metadados, enviar e-mails.. uma tabela de jobs no PostgreSQL é mais do que suficiente.

A parte que a maioria dos desenvolvedores não percebe: a reivindicação concorrente e segura já vem embutida no próprio banco.

No Alexandryn, uma biblioteca digital pessoal e auto-hospedada, essa escolha arquitetural salvou nossos modelos de distribuição desktop e homelab do colapso operacional.

Aqui está por que abandonamos a cartilha do Redis, como o `SKIP LOCKED` opera por baixo dos panos e como construir uma fila pronta para produção com leases renováveis e fencing criptográfico.

## 1. Por Que Equipes Buscam Filas (e a Armadilha da Escrita Dupla)

Uma fila de segundo plano cumpre quatro funções essenciais:

1. **Armazena tarefas** até que um worker esteja disponível para processá-las.
2. **Sobrevive a falhas catastróficas**, garantindo que o trabalho aceito nunca se perca.
3. **Executa novas tentativas com backoff** em vez de descartar tarefas com erro.
4. **Isola workers concorrentes**, para que múltiplos processos jamais disputem o mesmo registro.

No instante em que um usuário joga 400 arquivos EPUB no Alexandryn, o reflexo clássico é subir o Redis.

Extrair capas embutidas, processar manifests XML do OPF, calcular hashes de integridade e cruzar metadados com a API do Open Library não pode rodar dentro do ciclo HTTP. Fazer isso congela a interface web e derruba conexões TCP.

Só que esse reflexo impõe um custo operacional pesado.

O Alexandryn roda no hardware do próprio usuário: Electron no macOS, Windows e Linux, além de containers Docker headless em servidores unRAID, TrueNAS e Raspberry Pi.

Adicionar um daemon do Redis significa:

- Gerenciar scripts de supervisão de processos específicos para cada sistema operacional.
- Lidar com colisões locais de porta quando um desenvolvedor já roda Redis na porta `6379`.
- Queimar 60 MB de memória RAM ociosa nos notebooks dos usuários.
- Adicionar mais um container no `docker-compose.yml` suscetível a falhas em reinícios de rede.

Pior ainda: uma fila externa divide o seu sistema em dois mundos.

O job fica no Redis. O registro do livro fica no PostgreSQL. Nenhuma transação ACID abrange os dois armazenamentos simultaneamente.

Veja os dois cenários de falha por escrita dupla (dual-write hazard):

```text
Cenário A: Banco Primeiro, Fila Depois
Requisição HTTP
     │
     ▼
[Passo 1: COMMIT Transação PostgreSQL] ──> Grava registro do livro #4812
     │
     ▼  <── Processo morto por OOM, queda de energia ou erro de rede!
[Passo 2: Enfileira job no Redis]      ──> (NUNCA OCORRE)
```

O banco mantém um livro gravado que jamais terá sua capa extraída ou seus metadados indexados. Um registro órfão permanente.

Inverta a sequência:

```text
Cenário B: Fila Primeiro, Banco Depois
Requisição HTTP
     │
     ▼
[Passo 1: Enfileira job no Redis]      ──> Job criado para o livro #4812
     │
     ▼  <── Disco cheio, erro de chave única ou rollback no banco!
[Passo 2: COMMIT Transação PostgreSQL] ──> (FALHA)
```

O worker consome o job do Redis, busca o livro #4812 no PostgreSQL, encontra zero linhas e entra em pânico. Um job fantasma.

A solução padrão da indústria para esse impasse é o padrão **Transactional Outbox**: você grava os jobs em uma tabela de outbox no próprio PostgreSQL, roda um processo publicador para monitorar essa tabela e repassa os eventos para o Redis, gerenciando confirmações em duas fases.

Uma tabela de outbox no PostgreSQL alimentando um broker externo já é uma fila de jobs. Adicionar o Redis por cima é apenas complexidade acidental.

Mantenha a fila inteira dentro do PostgreSQL e o problema simplesmente desaparece.

No Alexandryn (ADR 0014), enfileirar o trabalho em segundo plano e alterar o estado da biblioteca compartilham exatamente a mesma transação do banco:

```sql
BEGIN;

INSERT INTO books (id, title, file_path, status)
VALUES ($1, $2, $3, 'importing');

INSERT INTO jobs (queue, payload, status)
VALUES ('metadata-fetch', jsonb_build_object('book_id', $1), 'pending');

COMMIT;
```

Se a transação passar, o livro e o job passam a existir simultaneamente. Se a transação sofrer rollback, o job é descartado na hora.

Zero tarefas órfãs. Zero execuções fantasmas. Zero custo de transações distribuídas em duas fases.

## 2. O Que o `FOR UPDATE SKIP LOCKED` Faz de Fato

A parte difícil de uma fila baseada em banco de dados é a reivindicação dos jobs, não o seu armazenamento.

Imagine dois workers consultando uma tabela de tarefas pendentes:

```sql
SELECT id, payload
FROM jobs
WHERE status = 'pending'
ORDER BY run_at ASC
LIMIT 1;
```

Ambos os workers executam essa consulta no mesmo milissegundo. Ambos leem o mesmo ID de linha. Ambos começam a extrair o mesmo arquivo EPUB.

O usuário recebe capas duplicadas, entradas duplicadas no banco e processamento desperdiçado.

Travar a linha com `FOR UPDATE` resolve a duplicidade:

```sql
SELECT id, payload
FROM jobs
WHERE status = 'pending'
ORDER BY run_at ASC
LIMIT 1
FOR UPDATE;
```

Essa trava impede processamento duplicado, mas gera um gargalo ainda pior: contenção de locks.

O Worker 1 trava a linha 1. O Worker 2, o Worker 3 e o Worker 4 ficam travados em fila indiana atrás do Worker 1. Eles são forçados a esperar o Worker 1 concluir toda a transação antes de sequer conseguir ler a linha 1.

Quando o Worker 1 commita e altera o status para `'running'`, o Worker 2 é liberado, descobre que a linha 1 não está mais `'pending'` e é obrigado a reiniciar a busca do zero. A concorrência cai para zero. Quatro workers passam a operar como uma única thread lenta.

O `SKIP LOCKED` muda completamente a dinâmica de aquisição de travas.

Em vez de bloquear esperando por uma linha travada, o PostgreSQL simplesmente ignora essa linha e retorna imediatamente o próximo registro desbloqueado que corresponda aos filtros da busca:

```sql
SELECT id, payload
FROM jobs
WHERE status = 'pending'
ORDER BY run_at ASC
LIMIT 1
FOR UPDATE SKIP LOCKED;
```

O PostgreSQL disponibiliza essa cláusula desde a versão 9.5 (janeiro de 2016).

Agora, quatro workers consultam a tabela no mesmo milissegundo:

- Worker 1 trava a linha 101.
- Worker 2 ignora a linha 101 e trava a linha 102.
- Worker 3 ignora as linhas 101 e 102, travando a linha 103.
- Worker 4 ignora as linhas 101, 102 e 103, travando a linha 104.

Ninguém espera. A contenção desaparece.

Mas atenção a um detalhe crucial: as travas de linha obtidas por um `FOR UPDATE` duram apenas enquanto a transação que as abriu estiver ativa. Se você roda em modo autocommit, a trava evapora assim que a instrução SQL é concluída.

O `SKIP LOCKED` é apenas metade do segredo. A outra metade é atualizar o status da linha para `'running'` na **mesma instrução SQL atômica**.

## 3. Construindo a Fila: Uma Tabela, Quatro Consultas

A fila completa opera com uma única tabela e quatro consultas SQL diretas.

### A Tabela

```sql
CREATE TABLE jobs (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    queue        VARCHAR(64) NOT NULL,
    payload      JSONB NOT NULL DEFAULT '{}',
    status       VARCHAR(20) NOT NULL DEFAULT 'pending', -- pending, running, retrying, completed, failed
    attempts     INT NOT NULL DEFAULT 0,
    max_attempts INT NOT NULL DEFAULT 5,
    run_at       TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    locked_until TIMESTAMPTZ,
    lease_token  UUID,
    last_error   TEXT,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- Indice parcial para buscas ultra-rapidas de reivindicacao
CREATE INDEX idx_jobs_claim ON jobs (run_at ASC)
WHERE status IN ('pending', 'retrying');

-- Indice para a varredura de leases expirados a cada 30 segundos
CREATE INDEX idx_jobs_reaper ON jobs (locked_until ASC)
WHERE status = 'running';
```

O índice parcial `idx_jobs_claim` cobre exclusivamente linhas nos status `pending` e `retrying`. Conforme as tarefas são concluídas, elas saem do índice. A consulta de claim nunca precisa varrer pilhas de tarefas já finalizadas.

### Consulta 1: Enfileirar (Enqueue)

Adicionar uma tarefa é um `INSERT` padrão:

```sql
INSERT INTO jobs (queue, payload)
VALUES ('metadata-fetch', '{"book_id": "4812", "file_path": "/books/duna.epub"}');
```

### Consulta 2: Reivindicação Atômica (Claim)

Esta é a consulta fundamental onde toda a fila se apoia:

```sql
UPDATE jobs
SET status = 'running',
    attempts = attempts + 1,
    locked_until = $1,     -- $now + lease de 60 segundos
    lease_token = $2,      -- novo UUID v4 exclusivo
    updated_at = $3        -- $now
WHERE id = (
    SELECT id
    FROM jobs
    WHERE status IN ('pending', 'retrying')
      AND run_at <= $3
    ORDER BY run_at ASC
    LIMIT 1
    FOR UPDATE SKIP LOCKED
)
RETURNING id, queue, payload, attempts, max_attempts, lease_token;
```

A subconsulta interna localiza a tarefa pendente mais antiga, ignora qualquer linha que outros workers já estejam travando e bloqueia apenas aquele registro.

O comando de `UPDATE` externo altera o status para `'running'`, define uma concessão de 60 segundos, atribui um `lease_token` exclusivo e retorna os dados para o worker.

Toda essa instrução executa em menos de 800 microssegundos. O worker assume posse exclusiva da tarefa e o lock da linha no banco é liberado imediatamente.

O worker processa a extração dos arquivos completamente fora de qualquer transação de banco de dados.

### Consulta 3: Concluir (Complete)

Quando o processamento tem sucesso, o worker marca a linha como finalizada:

```sql
UPDATE jobs
SET status = 'completed',
    locked_until = NULL,
    lease_token = NULL,
    updated_at = $now
WHERE id = $1 AND lease_token = $2;
```

### Consulta 4: Tentar Novamente com Backoff Exponencial (Retry)

Se a execução falhar, o worker calcula o intervalo de espera exponencial:

```text
espera = 2^tentativas * 5s
```

```sql
UPDATE jobs
SET status = CASE WHEN attempts >= max_attempts THEN 'failed' ELSE 'retrying' END,
    run_at = $now + make_interval(secs => power(2, attempts) * 5),
    locked_until = NULL,
    lease_token = NULL,
    last_error = $sanitized_error,
    updated_at = $now
WHERE id = $1 AND lease_token = $2;
```

Como o campo `run_at` avança no tempo, a tarefa aguarda o período de backoff antes que qualquer worker possa reivindicá-la novamente.

Se o número de `attempts` atingir `max_attempts`, a expressão `CASE` encaminha a tarefa direto para `'failed'`. Essa é a sua dead-letter queue. Você pode inspecionar os erros ou reprocessar registros usando comandos SQL simples.

## 4. Dois Workers Dividindo a Fila em Go

Veja esse mecanismo funcionando na prática sob concorrência em Go.

Abaixo está uma implementação completa e funcional com duas goroutines processando quatro tarefas simultâneas, simulando uma falha transiente, aguardando o backoff e concluindo com sucesso:

```go
package main

import (
	"context"
	"database/sql"
	"encoding/json"
	"errors"
	"fmt"
	"log"
	"math"
	"sync"
	"time"

	"github.com/google/uuid"
	_ "github.com/jackc/pgx/v5/stdlib"
)

type Job struct {
	ID          uuid.UUID
	Queue       string
	Payload     json.RawMessage
	Attempts    int
	MaxAttempts int
	LeaseToken  uuid.UUID
}

func claim(ctx context.Context, db *sql.DB, now time.Time) (*Job, error) {
	var j Job
	leaseToken := uuid.New()
	lockedUntil := now.Add(60 * time.Second)

	query := `
		UPDATE jobs
		SET status = 'running',
		    attempts = attempts + 1,
		    locked_until = $1,
		    lease_token = $2,
		    updated_at = $3
		WHERE id = (
			SELECT id FROM jobs
			WHERE status IN ('pending', 'retrying') AND run_at <= $3
			ORDER BY run_at ASC
			LIMIT 1
			FOR UPDATE SKIP LOCKED
		)
		RETURNING id, queue, payload, attempts, max_attempts, lease_token`

	err := db.QueryRowContext(ctx, query, lockedUntil, leaseToken, now).
		Scan(&j.ID, &j.Queue, &j.Payload, &j.Attempts, &j.MaxAttempts, &j.LeaseToken)

	if errors.Is(err, sql.ErrNoRows) {
		return nil, nil // Sem tarefas pendentes no momento
	}
	return &j, err
}

func complete(ctx context.Context, db *sql.DB, id, token uuid.UUID, now time.Time) error {
	res, err := db.ExecContext(ctx, `
		UPDATE jobs
		SET status = 'completed', locked_until = NULL, lease_token = NULL, updated_at = $1
		WHERE id = $2 AND lease_token = $3`,
		now, id, token,
	)
	if err != nil {
		return err
	}
	rows, _ := res.RowsAffected()
	if rows == 0 {
		return errors.New("lease expirado ou revogado; conclusao rejeitada")
	}
	return nil
}

func retry(ctx context.Context, db *sql.DB, id, token uuid.UUID, attempts, maxAttempts int, errMsg string, now time.Time) error {
	backoffSec := int(math.Pow(2, float64(attempts))) * 2
	nextRun := now.Add(time.Duration(backoffSec) * time.Second)
	status := "retrying"
	if attempts >= maxAttempts {
		status = "failed"
	}

	_, err := db.ExecContext(ctx, `
		UPDATE jobs
		SET status = $1, run_at = $2, locked_until = NULL, lease_token = NULL, last_error = $3, updated_at = $4
		WHERE id = $5 AND lease_token = $6`,
		status, nextRun, errMsg, now, id, token,
	)
	return err
}

func handleTask(j *Job) error {
	time.Sleep(150 * time.Millisecond)

	var p map[string]string
	_ = json.Unmarshal(j.Payload, &p)

	// Simula timeout de rede na primeira tentativa de sincronizacao
	if p["name"] == "sync-metadata" && j.Attempts == 1 {
		return errors.New("timeout ao conectar com openlibrary.org")
	}
	return nil
}

func worker(ctx context.Context, name string, db *sql.DB, wg *sync.WaitGroup) {
	defer wg.Done()
	idlePolls := 0

	for idlePolls < 15 {
		now := time.Now().UTC()
		job, err := claim(ctx, db, now)
		if err != nil {
			log.Printf("[%s] erro no claim: %v", name, err)
			time.Sleep(100 * time.Millisecond)
			continue
		}

		if job == nil {
			idlePolls++
			time.Sleep(100 * time.Millisecond)
			continue
		}

		idlePolls = 0
		if err := handleTask(job); err != nil {
			log.Printf("[%s] falha: %s (tentativa %d): %v", name, job.Queue, job.Attempts, err)
			_ = retry(ctx, db, job.ID, job.LeaseToken, job.Attempts, job.MaxAttempts, err.Error(), time.Now().UTC())
		} else {
			log.Printf("[%s] sucesso: %s (tentativa %d)", name, job.Queue, job.Attempts)
			_ = complete(ctx, db, job.ID, job.LeaseToken, time.Now().UTC())
		}
	}
}
```

Executando dois workers simultâneos contra as quatro tarefas, a saída é clara:

```text
[worker-1] sucesso: extract-cover (tentativa 1)
[worker-2] sucesso: parse-chapters (tentativa 1)
[worker-1] falha: sync-metadata (tentativa 1): timeout ao conectar com openlibrary.org
[worker-2] sucesso: calculate-hashes (tentativa 1)
... intervalo de backoff decorre (4 segundos) ...
[worker-2] sucesso: sync-metadata (tentativa 2)
```

Observe a tarefa `sync-metadata`: o `worker-1` tentou processá-la e encontrou uma falha de conexão. A tarefa entrou em backoff.

Quatro segundos depois, o `worker-2` assumiu a tarefa reescalonada e a concluiu com sucesso.

O estado vive inteiramente na tabela do banco. Qualquer worker retoma o trabalho exatamente de onde o anterior parou.

## 5. O Que Tutoriais Ignoram: A Realidade Crua de Produção

As quatro consultas acima funcionam no cenário feliz. Em produção com hardware real, as coisas quebram de maneiras imprevistas.

Três falhas específicas derrubam sistemas ingênuos:

### Problema 1: Recuperação de Crashes (A Tarefa Presa em Execução)

O que acontece quando o processo de um worker morre no meio da execução? Um OOM kill disparado pelo kernel, um kernel panic ou um cabo de força puxado da tomada.

Como a instrução de claim gravou `status = 'running'` antes de iniciar o trabalho pesado, nenhuma trava de banco fica aberta enquanto o worker processa.

Se o processo morrer, a linha fica congelada em `'running'` para sempre.

O Alexandryn resolve isso com um processo em segundo plano (**reaper**) que faz uma varredura a cada 30 segundos:

```sql
UPDATE jobs
SET status = 'retrying',
    run_at = $now,
    locked_until = NULL,
    lease_token = NULL,
    updated_at = $now
WHERE status = 'running'
  AND locked_until < $now;
```

Se uma tarefa permanece em `'running'` além do seu lease de 60 segundos, o worker é dado como morto. O reaper redefine a linha para `'retrying'` para que outro worker possa assumi-la.

### Problema 2: O Worker Zumbi e Fencing Criptográfico

O reaper resolve workers mortos, mas cria um problema ainda mais perigoso: **o worker zumbi**.

Imagine que o Worker A reivindique o Job 42 com um lease de 60 segundos.

O Worker A inicia o processamento de um EPUB pesado de 120 MB. O runtime do Go entra em uma pausa longa de garbage collection, ou uma chamada externa de rede fica travada em um socket TCP durante 65 segundos.

O Worker A não morreu. Ele está temporariamente congelado.

```text
T=00s: Worker A reivindica o Job 42 (lease até T=60s)
T=60s: Lease expira enquanto Worker A aguarda socket
T=62s: Reaper roda e redefine Job 42 para 'retrying'
T=63s: Worker B reivindica Job 42 (novo lease até T=123s)
T=70s: Worker A descongela! Conclui o trabalho e grava no banco.
T=72s: Worker B conclui o trabalho e grava no banco.
```

O Worker A e o Worker B executaram a mesma tarefa concorrentemente. O Worker A acordou atrasado e sobrescreveu o trabalho novo do Worker B com dados obsoletos.

Esse é o clássico risco de escritas divididas (split-brain) em sistemas distribuídos. Locks distribuídos sem tokens de fencing são falhos por definição.

O Alexandryn soluciona esse risco adotando **Fencing Criptográfico (`lease_token UUID`)** (Revisão 0036).

1. Cada reivindicação gera um novo UUID: o `lease_token`.
2. Durante a execução, tarefas longas enviam heartbeats a cada 20 segundos:
   ```sql
   UPDATE jobs
   SET locked_until = $now + INTERVAL '60 seconds', updated_at = $now
   WHERE id = $id AND lease_token = $token;
   ```
3. Ao concluir ou registrar falha, o worker impõe a validação do token:
   ```sql
   UPDATE jobs SET status = 'completed'
   WHERE id = $id AND lease_token = $token;
   ```

Se o reaper revogou o Job 42, ele rotacionou o `lease_token` da linha.

Quando o Worker A acordar e disparar a atualização de conclusão:

1. O PostgreSQL compara o token no banco com o token defasado do Worker A.
2. O PostgreSQL retorna: **0 linhas afetadas**.
3. O Worker A verifica `RowsAffected()`. Ao identificar `0`, percebe a perda da concessão, cancela seu `context.Context` e descarta arquivos temporários.

A gravação do Worker A é ignorada em silêncio sem corromper o banco.

### Problema 3: Testes sem `time.Sleep()`

Testar expiração de leases de 60 segundos ou backoff costuma gerar testes lentos e frágeis: desenvolvedores espalham chamadas a `time.Sleep(65 * time.Second)` pelos arquivos de teste.

Isso transforma uma suíte ágil em um gargalo de minutos. Testes lentos são simplesmente ignorados no dia a dia.

No Alexandryn (ADR 0014), o código da fila nunca chama `NOW()` no SQL nem `time.Now()` direto no Go.

Todas as consultas de claim, heartbeats e limpezas do reaper recebem um parâmetro `$now` explícito, fornecido por uma interface `Clock`:

```go
type Clock interface {
    Now() time.Time
}
```

Nos testes unitários, injetamos um mock de relógio determinístico:

```go
func TestReaperReclaimsExpiredLease(t *testing.T) {
    clk := clock.NewMock(time.Now())
    q := NewQueue(db, clk)

    job := q.Enqueue(ctx, "extract-cover", payload)
    claimed, _ := q.Claim(ctx, clk.Now())

    // Avanca 65 segundos no tempo instantaneamente: zero sleep!
    clk.Advance(65 * time.Second)

    reaped, _ := q.ReapExpiredLeases(ctx, clk.Now())
    require.Equal(t, 1, reaped)

    // Gravacao do worker defasado e sumariamente rejeitada
    err := q.Complete(ctx, claimed.ID, claimed.LeaseToken, clk.Now())
    require.ErrorIs(t, err, ErrLeaseExpired)
}
```

A suíte completa de testes.. validando claims, expirações de 60 segundos, recuperação pelo reaper e bloqueio de escritas defasadas.. executa em **40 milissegundos**.

## 6. Sanitização Central de Erros e Tipos Sentinela

Nem toda falha deve gerar novas tentativas.

Se o Open Library retornar HTTP 503, faz todo sentido aguardar com backoff exponencial. Se um arquivo EPUB tiver o cabeçalho ZIP corrompido, tentar dez vezes não consertará o arquivo. Só gastará bateria e ciclos de CPU.

Os handlers retornam erros sentinela:

```go
if errors.Is(err, epub.ErrCorruptZip) {
    return job.Permanent(fmt.Errorf("arquivo zip irrecuperavel: %w", err))
}
```

Quando o worker detecta um erro `Permanent`, ignora a política de novas tentativas e envia o registro direto para `'failed'`.

### Sanitização Centralizada

Mensagens gravadas em `jobs.last_error` são persistidas no disco e exibidas em painéis administrativos.

Mensagens de erro não tratadas vazam segredos com frequência:

- Caminhos do sistema operacional: `/Users/luann/.alexandryn/vault/livro.epub`
- Senhas de banco em strings de conexão que falharam
- Bearer tokens expostos em URLs de APIs

Antes de qualquer erro chegar ao PostgreSQL, ele passa por uma sanitização central com regex:

```go
var (
    pathRegex  = regexp.MustCompile(`(/Users|/home|[A-Za-z]:\\)[^\s"':]+`)
    dsnRegex   = regexp.MustCompile(`postgres://[^:]+:[^@]+@`)
    tokenRegex = regexp.MustCompile(`(Bearer|token=)[a-zA-Z0-9_\-\.]+`)
)

func sanitizeError(msg string) string {
    msg = dsnRegex.ReplaceAllString(msg, "postgres://[REDACTED]@")
    msg = tokenRegex.ReplaceAllString(msg, "$1[REDACTED]")
    msg = pathRegex.ReplaceAllString(msg, "[REDACTED_PATH]")
    if len(msg) > 1024 {
        msg = msg[:1021] + "..."
    }
    return msg
}
```

Os diagnósticos permanecem claros sem transformar o banco em uma fonte de vazamento de credenciais.

## 7. Higiene da Tabela e Pressão do Vacuum

Uma fila no PostgreSQL impõe uma realidade física que você deve respeitar: **dead tuples**.

Cada alteração de status (de `pending` para `running`, para `retrying`, para `completed`) é um comando de `UPDATE`. No PostgreSQL, um `UPDATE` não sobrescreve bytes no mesmo lugar; ele grava uma nova versão da linha e marca a versão anterior como morta.

Se você processa 5.000 tarefas por hora, gera 15.000 tuplas mortas a cada hora.

Três práticas impedem que o inchaço da tabela comprometa o desempenho:

1. **Indexação Parcial**:

   ```sql
   CREATE INDEX idx_jobs_claim ON jobs (run_at ASC)
   WHERE status IN ('pending', 'retrying');
   ```

   Tarefas concluídas saem desse índice na hora. O índice de busca permanece minúsculo e cabe inteiro na memória RAM.

2. **Limpeza Programada**:
   Tarefas concluídas não se excluem sozinhas. Agende uma consulta periódica para expurgar tarefas com mais de 7 dias:

   ```sql
   DELETE FROM jobs
   WHERE status = 'completed' AND updated_at < $now - INTERVAL '7 days';
   ```

3. **Autovacuum Agressivo**:
   Em filas com alta rotatividade de escrita, ajuste os parâmetros de armazenamento da tabela para que o autovacuum atue com frequência:
   ```sql
   ALTER TABLE jobs SET (
       autovacuum_vacuum_scale_factor = 0.05,
       autovacuum_vacuum_threshold = 500
   );
   ```

## Quando Você Realmente Precisa de um Broker Dedicado

Uma fila em PostgreSQL possui limites físicos claros. Reconheça-os antes de bater de frente com eles:

- **Vazão massiva e contínua**: se o seu sistema processa 50.000 jobs por segundo, a sobrecarga de vacuum do PostgreSQL vira um problema operacional sério. Nesses volumes, Redis ou RabbitMQ dominam.
- **Fan-out e streaming de eventos**: se dez microsserviços precisam de uma cópia independente de cada evento, você precisa de um log distribuído como Kafka, não de uma fila onde tarefas reivindicadas somem para os outros.
- **Conjuntos complexos de funcionalidades**: limites de concorrência por inquilino, janelas dinâmicas de rate-limiting e filas prioritárias complexas. Ferramentas como BullMQ já entregam tudo isso pronto.

Para o Alexandryn, nossa demanda real é processar lotes de até 400 livros por importação. Nossa fila em PostgreSQL processa 6.000 claims por segundo em SSDs NVMe convencionais. Isso é 200 vezes mais do que jamais precisaremos.

Em troca dessa escolha, conquistamos:

- 1 daemon a menos para supervisionar no macOS e Windows.
- 0 colisões de porta no ambiente do usuário.
- Importações 100% atômicas dentro de transações de banco unificadas.
- Zero risco de escrita dupla.
- Imunidade matemática a workers zumbis através de tokens de fencing.
- Testes unitários determinísticos em 40ms.

A regra de ouro: **comece com o banco de dados que você já roda**. Só migre para um broker externo quando você conseguir apontar com clareza o limite físico que está atingindo.
