_Why we rejected Redis and RabbitMQ in Alexandryn, and how we engineered an in-database job queue with PostgreSQL SKIP LOCKED, heartbeat leases, and fencing tokens to prevent zombie-worker bugs._

---

When building background workers, the industry reflex is immediate: spin up Redis with Sidekiq, Celery, or RabbitMQ.

That reflex makes sense at venture scale with dedicated operations teams. For a self-hosted desktop and homelab application, it was operational suicide.

Alexandryn runs on user hardware. It ships as an Electron desktop bundle for macOS, Windows, and Linux, and as a headless Docker container for unRAID, TrueNAS, and Raspberry Pi servers.

When a user imports 400 EPUB files, the system has heavy work to do. It must extract embedded cover art, parse OPF metadata trees, hash contents, and query the Open Library API. Doing that inside the HTTP request loop blocks the UI and drops TCP connections.

Background processing was mandatory. Adding another daemon was not.

Every extra background service added to a self-hosted app multiplies support tickets. On desktop systems, supervising a secondary Redis daemon introduces cross-platform process babysitting, port collision crashes, and 60 MB of idle RAM overhead. In Docker, every extra container in a Compose file is another moving part that fails during network restarts.

We already had PostgreSQL running under our Go supervisor (ADR 0002). We did not need another database. We needed to understand the concurrency primitives already waiting in the engine we had.

Here is how we built an atomic background job queue directly in PostgreSQL using `FOR UPDATE SKIP LOCKED`, heartbeat leases, and cryptographic fencing tokens.

---

## 1. The Dual-Write Trap: Why Postgres Beats Redis

Most systems pair a relational database with an external queue. That pairing introduces a silent distributed systems failure: the dual-write hazard.

Consider what happens during a library import with PostgreSQL and Redis:

```text
HTTP Request
     │
     ▼
[Step 1: BEGIN PostgreSQL Tx]
     │
     ├── Insert book record (id=4812)
     │
[Step 2: COMMIT PostgreSQL Tx]
     │
     ▼  <── Power loss, OOM kill, or network disconnect here!
[Step 3: Enqueue job to Redis] ──> (NEVER REACHED)
```

If the server crashes between Step 2 and Step 3, the database holds a book record that will never have its cover extracted or metadata indexed. An orphaned record.

Flip the sequence:

```text
HTTP Request
     │
     ▼
[Step 1: Enqueue job to Redis (book_id=4812)]
     │
     ▼  <── Database disk full, foreign key failure, or connection drop!
[Step 2: INSERT into PostgreSQL] ──> (FAILS & ROLLS BACK)
```

Now a background worker pops the job from Redis, attempts to find book ID 4812 in PostgreSQL, finds zero rows, and writes to dead letters. A phantom job.

Preventing this with Redis requires the Transactional Outbox pattern. You write an outbox table in Postgres, run a publisher process to relay rows to Redis, and manage two-phase acknowledgments.

That is accidental complexity. We eliminated the middleman.

In Alexandryn (ADR 0014), the queue is a table inside PostgreSQL. Enqueuing work and modifying library state happen in the exact same transactional boundary:

```sql
BEGIN;

INSERT INTO books (id, title, file_path, status)
VALUES ($1, $2, $3, 'importing');

INSERT INTO jobs (id, queue, payload, status, available_at)
VALUES ($4, 'metadata-fetch', $5, 'queued', $now);

COMMIT;
```

If the transaction commits, both the book and the job exist. If the transaction rolls back, the job vanishes cleanly. No orphaned tasks. No phantom runs. Zero two-phase commit overhead.

## 2. The Naive Mistake: Row Locks and Deadlocks

Building a queue in SQL sounds simple until you run concurrent workers.

Here was our naive first attempt:

```sql
-- DANGEROUS: High contention under concurrent workers
SELECT id, payload
FROM jobs
WHERE status = 'queued' AND available_at <= $now
ORDER BY available_at ASC
LIMIT 1;
```

Followed immediately in application code by:

```sql
UPDATE jobs SET status = 'running' WHERE id = $id;
```

It passed unit tests with a single worker. It collapsed under four concurrent worker goroutines.

All four workers polled at the same instant. All four read the same row ID. All four issued concurrent `UPDATE` statements on that exact row.

One worker acquired the lock. The other three blocked waiting for it. When the first worker committed, the other three failed their conditions, wasted database cycles, and produced deadlocks when workers updated records in differing orders.

Adding `FOR UPDATE` to the `SELECT` made it worse:

```sql
-- STILL BROKEN: Serializes every worker in line
SELECT id FROM jobs
WHERE status = 'queued' AND available_at <= $now
ORDER BY available_at ASC
LIMIT 1
FOR UPDATE;
```

Now Worker 1 held an exclusive lock on row 1. Worker 2, Worker 3, and Worker 4 queued behind Worker 1. They waited for Worker 1 to finish its transaction before they could even evaluate row 1.

Once Worker 1 committed `status = 'running'`, Worker 2 woke up, saw row 1 was no longer `'queued'`, and had to re-scan. Concurrency dropped to zero.

---

## 3. The Fix: PostgreSQL `SKIP LOCKED`

The solution has lived in PostgreSQL since version 9.5: `FOR UPDATE SKIP LOCKED`.

`SKIP LOCKED` changes lock acquisition behavior. If a matching row is locked by another active transaction, PostgreSQL does not wait. It skips that row instantly and moves to the next candidate in the index:

```sql
SELECT id, queue, payload, attempts
FROM jobs
WHERE status IN ('queued', 'retrying')
  AND available_at <= $1
ORDER BY available_at ASC
LIMIT 1
FOR UPDATE SKIP LOCKED;
```

Four workers query the table at the exact same millisecond:

- Worker 1 locks row 101.
- Worker 2 skips row 101 and locks row 102.
- Worker 3 skips rows 101 and 102, locking row 103.
- Worker 4 skips rows 101, 102, and 103, locking row 104.

Contention drops to zero.

Here is the critical performance invariant: **never hold the database row lock during job execution**.

An EPUB parser might chew on a 100 MB file for 15 seconds. If you hold the transaction open for 15 seconds, you starve database connections.

Alexandryn uses microsecond claim transactions:

```go
func (q *Queue) Claim(ctx context.Context, now time.Time) (*Job, error) {
    tx, err := q.db.BeginTx(ctx, nil)
    if err != nil {
        return nil, err
    }
    defer tx.Rollback()

    var j Job
    query := `
        SELECT id, queue, payload, attempts
        FROM jobs
        WHERE status IN ('queued', 'retrying')
          AND available_at <= $1
        ORDER BY available_at ASC
        LIMIT 1
        FOR UPDATE SKIP LOCKED`

    err = tx.QueryRowContext(ctx, query, now).Scan(&j.ID, &j.Queue, &j.Payload, &j.Attempts)
    if errors.Is(err, sql.ErrNoRows) {
        return nil, nil // No jobs waiting
    }
    if err != nil {
        return nil, err
    }

    j.LeaseToken = uuid.New()
    j.LockedUntil = now.Add(60 * time.Second)

    updateQuery := `
        UPDATE jobs
        SET status = 'running',
            locked_until = $1,
            lease_token = $2,
            attempts = attempts + 1,
            updated_at = $3
        WHERE id = $4`

    _, err = tx.ExecContext(ctx, updateQuery, j.LockedUntil, j.LeaseToken, now, j.ID)
    if err != nil {
        return nil, err
    }

    if err := tx.Commit(); err != nil {
        return nil, err
    }

    return &j, nil
}
```

The database transaction opens, claims the row, marks it running with a 60-second lease, generates a unique lease token, and commits.

Total time holding the PostgreSQL row lock: **under 800 microseconds**.

The worker then executes the book extraction outside any database transaction.

## 4. The Zombie Worker Bug: Cross-Spec Review 0036

During our cross-spec review (review 0036), we found a severe concurrency flaw.

What happens if a worker does not crash, but stops responding?

Suppose Worker A claims Job 42 with a 60-second lease (`locked_until = now + 60s`).

Worker A begins parsing a malformed PDF. The Go runtime encounters a heavy GC sweep, or an external HTTP call to Open Library hangs on a half-open TCP socket for 70 seconds.

Alexandryn runs a background **reaper process** every 30 seconds. The reaper sweeps for abandoned jobs:

```sql
SELECT id FROM jobs
WHERE status = 'running'
  AND locked_until < $now;
```

At second 62, the reaper runs. It sees Job 42's lease has expired. The reaper marks Job 42 back to `status = 'queued'`.

Worker B polls the database, claims Job 42, and begins processing.

At second 71, Worker A's network call unblocks. Worker A is unaware its lease expired. It finishes its work and writes its result to the database.

Worker B finishes two seconds later and writes its result.

```text
Timeline:
T=00s: Worker A claims Job 42 (lease until T=60s)
T=60s: Lease expires while Worker A hangs on socket
T=62s: Reaper reclaims Job 42, resets status to 'queued'
T=63s: Worker B claims Job 42 (new lease until T=123s)
T=71s: Worker A wakes up and commits writes ──> CORRUPTION HAZARD
T=73s: Worker B commits writes
```

Worker A and Worker B ran concurrently on the same job. Worker A's stale write clobbered Worker B's progress.

This is the classic zombie worker problem. Distributed locks without fencing tokens are broken by design.

## 5. The Solution: Cryptographic Fencing with `lease_token`

We solved this by turning the job lease into a cryptographic fence.

Every time a job is claimed or reclaimed, we generate a fresh UUID v4: the `lease_token`.

### Heartbeats

Long-running jobs must renew their lease. While the handler executes, a background goroutine sends a heartbeat query every 20 seconds:

```go
func (w *Worker) runHeartbeat(ctx context.Context, jobID uuid.UUID, token uuid.UUID) {
    ticker := time.NewTicker(20 * time.Second)
    defer ticker.Stop()

    for {
        select {
        case <-ctx.Done():
            return
        case <-ticker.C:
            now := w.clock.Now()
            newLock := now.Add(60 * time.Second)

            res, err := w.db.ExecContext(ctx, `
                UPDATE jobs
                SET locked_until = $1, updated_at = $2
                WHERE id = $3 AND lease_token = $4`,
                newLock, now, jobID, token,
            )
            if err != nil {
                w.logger.Warn("heartbeat failed", "job_id", jobID, "error", err)
                continue
            }

            rows, _ := res.RowsAffected()
            if rows == 0 {
                // Our lease was stolen by the reaper!
                w.logger.Error("lease stolen by reaper; aborting worker execution", "job_id", jobID)
                w.cancelCurrentJob()
                return
            }
        }
    }
}
```

If the reaper took the job, the row's `lease_token` was rotated. The heartbeat query matches zero rows. The worker immediately cancels its own execution context.

### Completion Fencing

When the handler finishes, it writes the completion status using the exact same fence:

```sql
UPDATE jobs
SET status = 'completed',
    completed_at = $now,
    locked_until = NULL,
    lease_token = NULL,
    updated_at = $now
WHERE id = $id AND lease_token = $lease_token;
```

Look at the `WHERE` clause: `WHERE id = $id AND lease_token = $lease_token`.

If Worker A stalls past 60 seconds, the reaper sweeps the job and hands it to Worker B with a new token.

When Worker A wakes up and attempts to commit:

1. PostgreSQL runs the update.
2. The `lease_token` does not match Worker A's stale token.
3. PostgreSQL reports: **0 rows affected**.
4. Worker A detects `rows == 0`, rolls back any staging files, and logs a stale lease warning.

Worker A's write drops silently without touching library records. Zero split-brain writes. Zero database corruption.

## 6. Deterministic Time Travel: 40ms Unit Tests

Testing distributed queues is notoriously frustrating. Engineers litter test files with `time.Sleep(65 * time.Second)` to test lease timeouts and backoff schedules.

That turns a 5-second test suite into a 3-minute bottleneck. Slow tests don't get run.

In Alexandryn (ADR 0014), the queue never calls SQL server-side `NOW()` or Go's `time.Now()`.

All claim queries, heartbeats, and reaper sweeps receive an explicit `$now` parameter supplied by an injected `Clock` interface:

```go
type Clock interface {
    Now() time.Time
}

type RealClock struct{}

func (RealClock) Now() time.Time {
    return time.Now().UTC()
}
```

In unit tests, we inject a deterministic mock clock:

```go
type MockClock struct {
    mu  sync.Mutex
    now time.Time
}

func NewMockClock(start time.Time) *MockClock {
    return &MockClock{now: start}
}

func (m *MockClock) Now() time.Time {
    m.mu.Lock()
    defer m.mu.Unlock()
    return m.now
}

func (m *MockClock) Advance(d time.Duration) {
    m.mu.Lock()
    defer m.mu.Unlock()
    m.now = m.now.Add(d)
}
```

Here is our test for the zombie reaper and fencing token:

```go
func TestReaperReclaimsExpiredLease(t *testing.T) {
    ctx := context.Background()
    clk := NewMockClock(time.Date(2026, 9, 22, 12, 0, 0, 0, time.UTC))
    q := NewTestQueue(t, clk)

    // 1. Enqueue and claim a job
    jobID := q.Enqueue(ctx, "test-task", []byte(`{}`))
    claimed, err := q.Claim(ctx, clk.Now())
    require.NoError(t, err)
    require.Equal(t, jobID, claimed.ID)

    // 2. Advance clock past the 60s lease window (no real sleep!)
    clk.Advance(65 * time.Second)

    // 3. Run reaper sweep
    reclaimedCount, err := q.ReapExpiredLeases(ctx, clk.Now())
    require.NoError(t, err)
    require.Equal(t, int64(1), reclaimedCount)

    // 4. Stale worker tries to complete with its old lease token
    err = q.Complete(ctx, claimed.ID, claimed.LeaseToken, clk.Now())
    require.ErrorIs(t, err, ErrLeaseExpired)

    // 5. Fresh worker claims the reclaimed job with a new token
    workerBClaim, err := q.Claim(ctx, clk.Now())
    require.NoError(t, err)
    require.NotEqual(t, claimed.LeaseToken, workerBClaim.LeaseToken)
}
```

This test verifies the claim, the lease expiration, the reaper sweep, the stale write rejection, and the secondary worker re-claim.

Total execution time: **42 milliseconds**.

No sleeping goroutines. No race conditions in CI. Pure, deterministic time travel.

## 7. Error Redaction and Sentinels

Not all errors are equal. If an external API returns HTTP 503, the job should retry with exponential backoff:

```text
delay = 2^attempts * 5s
```

If an imported EPUB has a corrupted header and cannot be unzipped, retrying ten times will never fix the file. It only wastes CPU cycles and battery.

Alexandryn handlers use sentinel errors:

```go
type PermanentError struct {
    Err error
}

func (e PermanentError) Error() string { return e.Err.Error() }
func (e PermanentError) Unwrap() error { return e.Err }

func Permanent(err error) error {
    return PermanentError{Err: err}
}
```

Inside the worker loop:

```go
if errors.As(err, &permErr) {
    // Jump straight to dead-letter queue; do not retry
    q.MarkDeadLetter(ctx, job.ID, job.LeaseToken, sanitizeError(err.Error()))
    return
}
```

### Unconditional Error Redaction

Error messages written to `jobs.last_error` are displayed in the admin dashboard and persisted to disk.

Raw error strings frequently leak sensitive data:

- Local filesystem paths: `/Users/luann/.alexandryn/library/secret.epub`
- Database credentials from failed connection strings
- Authorization tokens in failed HTTP URLs

Before any error string is saved to PostgreSQL, it passes through an error redactor:

```go
var (
    pathRegex  = regexp.MustCompile(`(/Users|/home|[A-Za-z]:\\)[^\s"':]+`)
    dsnRegex   = regexp.MustCompile(`postgres://[^:]+:[^@]+@`)
    tokenRegex = regexp.MustCompile(`(Bearer|token=)[a-zA-Z0-9_\-\.]+`)
)

func sanitizeError(msg string) string {
    msg = dsnRegex.ReplaceAllString(msg, "postgres://[REDACTED]@")
    msg = tokenRegex.ReplaceAllString(msg, "$1[REDACTED]")
    msg = pathRegex.ReplaceAllString(msg, "[REDACTED_PATH]")
    if len(msg) > 1024 {
        msg = msg[:1021] + "..."
    }
    return msg
}
```

The database stores only sanitized error messages. Diagnostics remain useful without turning the jobs table into an information leak.

## 8. The Production Blueprint

Here is the exact schema running in Alexandryn production:

```sql
CREATE TABLE jobs (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    queue VARCHAR(64) NOT NULL,
    payload JSONB NOT NULL DEFAULT '{}',
    status VARCHAR(20) NOT NULL DEFAULT 'queued', -- queued, running, retrying, completed, dead_letter
    attempts INT NOT NULL DEFAULT 0,
    max_attempts INT NOT NULL DEFAULT 5,
    available_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    locked_until TIMESTAMPTZ,
    lease_token UUID,
    last_error TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    completed_at TIMESTAMPTZ
);

-- The critical index for SKIP LOCKED claim throughput
CREATE INDEX idx_jobs_claim ON jobs (available_at ASC)
WHERE status IN ('queued', 'retrying');

-- The index for 30s reaper sweeps
CREATE INDEX idx_jobs_reaper ON jobs (locked_until ASC)
WHERE status = 'running';
```

Our worker pool configuration:

- **Pool size**: 4 concurrent worker goroutines.
- **Poll interval**: 2 seconds when idle (falls back immediately to next job when available).
- **Lease duration**: 60 seconds.
- **Heartbeat interval**: 20 seconds.
- **Reaper sweep**: Every 30 seconds.
- **Retention**: Completed jobs pruned after 7 days.

## What We Learned

We gave up Redis's raw throughput. Redis can process 100,000 operations per second in memory. Our PostgreSQL queue processes roughly 6,000 claims per second on commodity SSDs.

For a self-hosted digital library managing 30,000 books, 6,000 jobs per second is 200 times what we will ever need.

In exchange, we gained:

- Zero extra container dependencies.
- Zero extra daemon supervision scripts on macOS and Windows.
- 100% atomic imports through unified database transactions.
- Zero dual-write hazards.
- Mathematical immunity to zombie workers through cryptographic fencing tokens.
- Deterministic 40ms unit tests without a single `time.Sleep()`.

Before reaching for an external queue infrastructure, inspect your relational database. Concurrency primitives like `SKIP LOCKED` and atomic transactions solve the problem with fewer moving parts and zero distributed hazards.
