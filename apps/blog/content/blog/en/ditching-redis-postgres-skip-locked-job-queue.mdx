_Moving work off the request path usually starts with a reflex: spin up Redis. In Alexandryn, a single PostgreSQL table and FOR UPDATE SKIP LOCKED gave us atomic jobs, zero dual-writes, and heartbeat fencing without a second daemon._

---

PostgreSQL can run a reliable background job queue. The key is one clause: `FOR UPDATE SKIP LOCKED`.

One table, a handful of short queries, and zero message brokers to deploy, monitor, or babysit.

Moving work off the HTTP request path usually starts with a familiar question: do you need Redis with Celery, Sidekiq, BullMQ, or RabbitMQ?

If your application already uses PostgreSQL, the answer is often no.

For the background work most applications actually have.. generating exports, parsing uploaded files, delivering webhooks, extracting metadata, sending emails.. a jobs table in PostgreSQL is plenty.

The part most engineers miss: safe concurrent claiming is already built into the engine.

In Alexandryn, a personal, self-hosted digital library, that single architectural choice saved our desktop and homelab deployment models from operational collapse.

Here is why we ditched the Redis playbook, how `SKIP LOCKED` works under the hood, and how to build a production queue with heartbeat leases and cryptographic fencing.

---

## 1. Why Teams Reach for a Queue (and the Dual-Write Trap)

A background job queue does four things:

1. **Stores work** until a worker is ready to process it.
2. **Survives crashes**, so accepted work is never lost.
3. **Retries failures** with backoff instead of dropping tasks.
4. **Isolates concurrent workers**, so multiple routines never step on each other.

The moment a user drops 400 EPUB files into Alexandryn, the reflex is to add Redis.

Extracting embedded cover art, parsing OPF XML manifests, hashing bytes, and matching records against Open Library cannot run inside the HTTP loop. Doing that freezes the browser and drops connections.

That reflex carries a steep operational tax.

Alexandryn runs on user hardware: Electron on macOS, Windows, and Linux, plus headless Docker containers on unRAID, TrueNAS, and Raspberry Pi servers.

Adding a Redis daemon means:

- Managing platform-specific background service supervisors.
- Handling local port collisions when a developer already runs Redis on port `6379`.
- Burning 60 MB of idle RAM on user laptops.
- Adding another moving container to `docker-compose.yml` that can fail during network restarts.

Even worse, an external queue splits your system in two.

The job lives in Redis. The library record it refers to lives in PostgreSQL. No database transaction spans both datastores.

Look at the two dual-write failure modes:

```text
Pattern A: Database First, Queue Second
HTTP Request
     │
     ▼
[Step 1: COMMIT PostgreSQL Tx] ──> Inserts book record #4812
     │
     ▼  <── Process killed, power outage, or Redis connection reset!
[Step 2: Enqueue into Redis]   ──> (NEVER HAPPENS)
```

The database holds a book record that will never have its cover extracted. An orphaned record.

Flip the sequence:

```text
Pattern B: Queue First, Database Second
HTTP Request
     │
     ▼
[Step 1: Enqueue into Redis]   ──> Job created for book #4812
     │
     ▼  <── Disk full, unique constraint violation, or rollback!
[Step 2: COMMIT PostgreSQL Tx] ──> (FAILS)
```

A background worker pops the job from Redis, queries PostgreSQL for book #4812, finds zero rows, and panics. A phantom job.

The standard industry fix for this is the **Transactional Outbox** pattern: you write jobs to an outbox table in PostgreSQL, run an extra relay worker to poll that table, push rows into Redis, and manage acknowledgments.

An outbox table in PostgreSQL feeding an external broker is already a job queue. Adding Redis on top is just accidental complexity.

Keep the queue inside PostgreSQL. The problem vanishes.

In Alexandryn (ADR 0014), enqueuing background work and mutating library state share the exact same database transaction:

```sql
BEGIN;

INSERT INTO books (id, title, file_path, status)
VALUES ($1, $2, $3, 'importing');

INSERT INTO jobs (queue, payload, status)
VALUES ('metadata-fetch', jsonb_build_object('book_id', $1), 'pending');

COMMIT;
```

If the transaction commits, both the book and the job exist. If the transaction rolls back, the job disappears automatically.

Zero orphaned tasks. Zero phantom runs. Zero two-phase commit overhead.

## 2. What `FOR UPDATE SKIP LOCKED` Actually Does

The hard part of a database-backed queue is claiming jobs, not storing them.

Suppose two workers poll a pending jobs table:

```sql
SELECT id, payload
FROM jobs
WHERE status = 'pending'
ORDER BY run_at ASC
LIMIT 1;
```

Both workers run the query at the exact same millisecond. Both read the same row ID. Both begin extracting the same EPUB.

Your user gets duplicate covers, duplicate database entries, and wasted CPU.

Locking the candidate row with `FOR UPDATE` fixes the duplicate:

```sql
SELECT id, payload
FROM jobs
WHERE status = 'pending'
ORDER BY run_at ASC
LIMIT 1
FOR UPDATE;
```

This prevents duplicate processing, but creates a worse bottleneck: lock contention.

Worker 1 locks row 1. Worker 2, Worker 3, and Worker 4 block behind Worker 1. They wait until Worker 1 finishes its entire transaction before they can even inspect row 1.

Once Worker 1 commits and marks row 1 as `'running'`, Worker 2 wakes up, discovers row 1 is no longer `'pending'`, and rescans. Concurrency drops to zero. Four workers behave like one slow thread.

`SKIP LOCKED` changes lock acquisition completely.

Instead of waiting for a locked row, PostgreSQL skips it instantly and returns the next unlocked row that matches the query predicate:

```sql
SELECT id, payload
FROM jobs
WHERE status = 'pending'
ORDER BY run_at ASC
LIMIT 1
FOR UPDATE SKIP LOCKED;
```

PostgreSQL shipped this clause in version 9.5 (January 2016).

Now, four workers query the table at the exact same millisecond:

- Worker 1 locks row 101.
- Worker 2 skips row 101 and locks row 102.
- Worker 3 skips rows 101 and 102, locking row 103.
- Worker 4 skips rows 101, 102, and 103, locking row 104.

Nobody waits. Contention drops to zero.

Here is the caveat: row locks held by `FOR UPDATE` vanish the moment the transaction commits. If you run in autocommit, the lock dies when the statement finishes.

`SKIP LOCKED` is half the mechanism. The other half is flipping the row status to `'running'` in the **exact same atomic statement**.

## 3. Build the Queue: One Table, Four Queries

The entire queue runs on a single table and four SQL queries.

### The Table

```sql
CREATE TABLE jobs (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    queue        VARCHAR(64) NOT NULL,
    payload      JSONB NOT NULL DEFAULT '{}',
    status       VARCHAR(20) NOT NULL DEFAULT 'pending', -- pending, running, retrying, completed, failed
    attempts     INT NOT NULL DEFAULT 0,
    max_attempts INT NOT NULL DEFAULT 5,
    run_at       TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    locked_until TIMESTAMPTZ,
    lease_token  UUID,
    last_error   TEXT,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- Partial index for high-throughput claims
CREATE INDEX idx_jobs_claim ON jobs (run_at ASC)
WHERE status IN ('pending', 'retrying');

-- Index for the 30-second expired lease sweeper
CREATE INDEX idx_jobs_reaper ON jobs (locked_until ASC)
WHERE status = 'running';
```

The partial index `idx_jobs_claim` covers only `pending` and `retrying` rows. As jobs complete, the index stays tiny. The claim query never wades through thousands of completed history rows.

### Query 1: Enqueue

Enqueueing a job is a plain `INSERT`:

```sql
INSERT INTO jobs (queue, payload)
VALUES ('metadata-fetch', '{"book_id": "4812", "file_path": "/books/dune.epub"}');
```

### Query 2: Atomic Claim

This is the query the entire queue rests upon:

```sql
UPDATE jobs
SET status = 'running',
    attempts = attempts + 1,
    locked_until = $1,     -- $now + 60 seconds lease
    lease_token = $2,      -- fresh random UUID v4
    updated_at = $3        -- $now
WHERE id = (
    SELECT id
    FROM jobs
    WHERE status IN ('pending', 'retrying')
      AND run_at <= $3
    ORDER BY run_at ASC
    LIMIT 1
    FOR UPDATE SKIP LOCKED
)
RETURNING id, queue, payload, attempts, max_attempts, lease_token;
```

The nested subquery finds the oldest due job, skips any rows locked by other active workers, and locks it.

The outer `UPDATE` flips the status to `'running'`, stamps a 60-second lease, assigns a unique `lease_token`, and returns the row.

This statement executes in under 800 microseconds. The worker owns the job outright. The database row lock is released immediately.

The worker parses files outside any database transaction.

### Query 3: Complete

When the task succeeds, the worker marks the row completed:

```sql
UPDATE jobs
SET status = 'completed',
    locked_until = NULL,
    lease_token = NULL,
    updated_at = $now
WHERE id = $1 AND lease_token = $2;
```

### Query 4: Retry with Backoff

When an operation fails, the worker calculates an exponential backoff interval:

```text
delay = 2^attempts * 5s
```

```sql
UPDATE jobs
SET status = CASE WHEN attempts >= max_attempts THEN 'failed' ELSE 'retrying' END,
    run_at = $now + make_interval(secs => power(2, attempts) * 5),
    locked_until = NULL,
    lease_token = NULL,
    last_error = $sanitized_error,
    updated_at = $now
WHERE id = $1 AND lease_token = $2;
```

Because `run_at` moves into the future, the job waits out its backoff before any worker can claim it again.

If `attempts` reaches `max_attempts`, the `CASE` statement moves the job straight to `'failed'`. That is your dead-letter queue. You can inspect or requeue it using standard SQL.

## 4. Watch Two Workers Share a Queue in Go

Let's watch this handle concurrent execution in Go.

Here is a minimal, complete implementation demonstrating two workers picking up four jobs, handling a failure, backing off, and completing:

```go
package main

import (
	"context"
	"database/sql"
	"encoding/json"
	"errors"
	"fmt"
	"log"
	"math"
	"sync"
	"time"

	"github.com/google/uuid"
	_ "github.com/jackc/pgx/v5/stdlib"
)

type Job struct {
	ID          uuid.UUID
	Queue       string
	Payload     json.RawMessage
	Attempts    int
	MaxAttempts int
	LeaseToken  uuid.UUID
}

func claim(ctx context.Context, db *sql.DB, now time.Time) (*Job, error) {
	var j Job
	leaseToken := uuid.New()
	lockedUntil := now.Add(60 * time.Second)

	query := `
		UPDATE jobs
		SET status = 'running',
		    attempts = attempts + 1,
		    locked_until = $1,
		    lease_token = $2,
		    updated_at = $3
		WHERE id = (
			SELECT id FROM jobs
			WHERE status IN ('pending', 'retrying') AND run_at <= $3
			ORDER BY run_at ASC
			LIMIT 1
			FOR UPDATE SKIP LOCKED
		)
		RETURNING id, queue, payload, attempts, max_attempts, lease_token`

	err := db.QueryRowContext(ctx, query, lockedUntil, leaseToken, now).
		Scan(&j.ID, &j.Queue, &j.Payload, &j.Attempts, &j.MaxAttempts, &j.LeaseToken)

	if errors.Is(err, sql.ErrNoRows) {
		return nil, nil // No jobs due
	}
	return &j, err
}

func complete(ctx context.Context, db *sql.DB, id, token uuid.UUID, now time.Time) error {
	res, err := db.ExecContext(ctx, `
		UPDATE jobs
		SET status = 'completed', locked_until = NULL, lease_token = NULL, updated_at = $1
		WHERE id = $2 AND lease_token = $3`,
		now, id, token,
	)
	if err != nil {
		return err
	}
	rows, _ := res.RowsAffected()
	if rows == 0 {
		return errors.New("lease expired or stolen; completion rejected")
	}
	return nil
}

func retry(ctx context.Context, db *sql.DB, id, token uuid.UUID, attempts, maxAttempts int, errMsg string, now time.Time) error {
	backoffSec := int(math.Pow(2, float64(attempts))) * 2
	nextRun := now.Add(time.Duration(backoffSec) * time.Second)
	status := "retrying"
	if attempts >= maxAttempts {
		status = "failed"
	}

	_, err := db.ExecContext(ctx, `
		UPDATE jobs
		SET status = $1, run_at = $2, locked_until = NULL, lease_token = NULL, last_error = $3, updated_at = $4
		WHERE id = $5 AND lease_token = $6`,
		status, nextRun, errMsg, now, id, token,
	)
	return err
}

func handleTask(j *Job) error {
	time.Sleep(150 * time.Millisecond)

	var p map[string]string
	_ = json.Unmarshal(j.Payload, &p)

	// Simulate transient network failure on first attempt
	if p["name"] == "sync-metadata" && j.Attempts == 1 {
		return errors.New("openlibrary.org connection timed out")
	}
	return nil
}

func worker(ctx context.Context, name string, db *sql.DB, wg *sync.WaitGroup) {
	defer wg.Done()
	idlePolls := 0

	for idlePolls < 15 {
		now := time.Now().UTC()
		job, err := claim(ctx, db, now)
		if err != nil {
			log.Printf("[%s] claim error: %v", name, err)
			time.Sleep(100 * time.Millisecond)
			continue
		}

		if job == nil {
			idlePolls++
			time.Sleep(100 * time.Millisecond)
			continue
		}

		idlePolls = 0
		if err := handleTask(job); err != nil {
			log.Printf("[%s] failed: %s (attempt %d): %v", name, job.Queue, job.Attempts, err)
			_ = retry(ctx, db, job.ID, job.LeaseToken, job.Attempts, job.MaxAttempts, err.Error(), time.Now().UTC())
		} else {
			log.Printf("[%s] done: %s (attempt %d)", name, job.Queue, job.Attempts)
			_ = complete(ctx, db, job.ID, job.LeaseToken, time.Now().UTC())
		}
	}
}
```

Run two workers concurrently against four jobs. Here is the output:

```text
[worker-1] done: extract-cover (attempt 1)
[worker-2] done: parse-chapters (attempt 1)
[worker-1] failed: sync-metadata (attempt 1): openlibrary.org connection timed out
[worker-2] done: calculate-hashes (attempt 1)
... backoff passes (4 seconds) ...
[worker-2] done: sync-metadata (attempt 2)
```

Look at `sync-metadata`: `worker-1` attempted the job and failed. The job entered backoff.

Four seconds later, `worker-2` picked up the retried job and succeeded.

State lives in the table. Any worker can resume where another left off.

## 5. What Tutorial Demos Skip: The Hard Production Realities

The four queries above work in happy-path scenarios. In production, real hardware fails in messy ways.

Three specific failure modes break naive implementations:

### Problem 1: Crash Recovery (The Orphaned Running Job)

What happens if a worker process dies mid-task? An operating system OOM kill, a kernel panic, or a pulled power cord.

Because the claim query committed `status = 'running'` before executing, no database lock is held while the worker runs.

If the worker dies, the row sits in `'running'` forever.

Alexandryn solves this with an explicit background **reaper process** sweeping every 30 seconds:

```sql
UPDATE jobs
SET status = 'retrying',
    run_at = $now,
    locked_until = NULL,
    lease_token = NULL,
    updated_at = $now
WHERE status = 'running'
  AND locked_until < $now;
```

If a job has been in `'running'` longer than its 60-second lease, the worker is assumed dead. The reaper resets the row to `'retrying'` so another worker picks it up.

### Problem 2: The Zombie Worker and Cryptographic Fencing

The reaper fixes dead workers. It creates an even worse problem: **the zombie worker**.

Suppose Worker A claims Job 42 with a 60-second lease.

Worker A begins parsing a massive 120 MB EPUB. The Go runtime encounters a heavy garbage collection sweep, or an external HTTP call hangs on a stalled TCP socket for 65 seconds.

Worker A is not dead. It is paused.

```text
T=00s: Worker A claims Job 42 (lease until T=60s)
T=60s: Lease expires while Worker A hangs on TCP socket
T=62s: Reaper sweeps table, resets Job 42 to 'retrying'
T=63s: Worker B claims Job 42 (new lease until T=123s)
T=70s: Worker A unfreezes! Finishes work and writes result.
T=72s: Worker B finishes work and writes result.
```

Worker A and Worker B both executed Job 42. Worker A woke up and overwrote Worker B's fresh progress with stale data.

This is the classic distributed systems split-brain write hazard. Distributed locks without fencing tokens are broken by design.

Alexandryn solves this using **Cryptographic Fencing (`lease_token UUID`)** (Review 0036).

1. Every claim generates a fresh UUID: `lease_token`.
2. While running, long jobs heartbeat every 20 seconds:
   ```sql
   UPDATE jobs
   SET locked_until = $now + INTERVAL '60 seconds', updated_at = $now
   WHERE id = $id AND lease_token = $token;
   ```
3. When completing or retrying, the update enforces the fence:
   ```sql
   UPDATE jobs SET status = 'completed'
   WHERE id = $id AND lease_token = $token;
   ```

If the reaper stole Job 42, it rotated the row's `lease_token`.

When Worker A unpauses and runs its completion query:

1. PostgreSQL finds `lease_token != Worker_A_Token`.
2. PostgreSQL reports: **0 rows affected**.
3. Worker A checks `RowsAffected()`. It sees `0`, detects the theft, cancels its Go context, and drops its staging files.

Worker A's write drops silently without corrupting the database.

### Problem 3: Testing Without `time.Sleep()`

Testing a 60-second lease expiration or exponential backoff usually produces terrible tests: engineers sprinkle `time.Sleep(65 * time.Second)` across their test files.

That turns a 5-second test suite into a 3-minute bottleneck. Slow tests don't get run.

Alexandryn (ADR 0014) never calls SQL server-side `NOW()` or Go's `time.Now()`.

Every claim query, heartbeat, and reaper sweep takes an explicit `$now` parameter supplied by an injected `Clock` interface:

```go
type Clock interface {
    Now() time.Time
}
```

In unit tests, we inject a mock clock:

```go
func TestReaperReclaimsExpiredLease(t *testing.T) {
    clk := clock.NewMock(time.Now())
    q := NewQueue(db, clk)

    job := q.Enqueue(ctx, "extract-cover", payload)
    claimed, _ := q.Claim(ctx, clk.Now())

    // Fast-forward 65 seconds instantly: zero sleeping!
    clk.Advance(65 * time.Second)

    reaped, _ := q.ReapExpiredLeases(ctx, clk.Now())
    require.Equal(t, 1, reaped)

    // Stale worker completion rejected
    err := q.Complete(ctx, claimed.ID, claimed.LeaseToken, clk.Now())
    require.ErrorIs(t, err, ErrLeaseExpired)
}
```

The entire test suite.. verifying claims, 60-second timeouts, reaper sweeps, and stale write fencing.. runs in **40 milliseconds**.

## 6. Error Redaction and Sentinels

Not all errors should be retried.

If Open Library returns HTTP 503, retrying with exponential backoff makes sense. If an imported EPUB has a corrupted ZIP header, retrying ten times will never fix the file. It only wastes CPU cycles.

Handlers return sentinel errors:

```go
if errors.Is(err, epub.ErrCorruptZip) {
    return job.Permanent(fmt.Errorf("unrecoverable zip archive: %w", err))
}
```

When the worker catches a `Permanent` error, it bypasses retry backoff and moves the job straight to `'failed'`.

### Unconditional Error Redaction

Error messages written to `jobs.last_error` are persisted to disk and displayed in UI panels.

Raw error messages frequently leak secrets:

- Local filesystem paths: `/Users/luann/.alexandryn/vault/book.epub`
- Database passwords in failed DSN connection strings
- Bearer tokens in failed API calls

Before any error string touches PostgreSQL, it passes through a central sanitization function:

```go
var (
    pathRegex  = regexp.MustCompile(`(/Users|/home|[A-Za-z]:\\)[^\s"':]+`)
    dsnRegex   = regexp.MustCompile(`postgres://[^:]+:[^@]+@`)
    tokenRegex = regexp.MustCompile(`(Bearer|token=)[a-zA-Z0-9_\-\.]+`)
)

func sanitizeError(msg string) string {
    msg = dsnRegex.ReplaceAllString(msg, "postgres://[REDACTED]@")
    msg = tokenRegex.ReplaceAllString(msg, "$1[REDACTED]")
    msg = pathRegex.ReplaceAllString(msg, "[REDACTED_PATH]")
    if len(msg) > 1024 {
        msg = msg[:1021] + "..."
    }
    return msg
}
```

Diagnostics remain clear without turning the database into an information leak.

## 7. Table Hygiene and Vacuum Pressure

A PostgreSQL queue has one physical reality you must respect: **dead tuples**.

Every status change (from `pending` to `running`, to `retrying`, to `completed`) is an `UPDATE`. In PostgreSQL, an `UPDATE` does not overwrite data in place; it writes a new row version and marks the old one dead.

If you process 5,000 jobs per hour, you create 15,000 dead tuples per hour.

Two practices keep table bloat from degrading performance:

1. **Partial Indexing**:

   ```sql
   CREATE INDEX idx_jobs_claim ON jobs (run_at ASC)
   WHERE status IN ('pending', 'retrying');
   ```

   Completed rows drop out of this index immediately. The claim query index stays small and sits entirely in RAM.

2. **Scheduled Pruning**:
   Completed jobs never delete themselves. Run a periodic query to purge successful jobs older than 7 days:

   ```sql
   DELETE FROM jobs
   WHERE status = 'completed' AND updated_at < $now - INTERVAL '7 days';
   ```

3. **Aggressive Autovacuum**:
   On high-churn queues, adjust table storage parameters so autovacuum runs frequently:
   ```sql
   ALTER TABLE jobs SET (
       autovacuum_vacuum_scale_factor = 0.05,
       autovacuum_vacuum_threshold = 500
   );
   ```

## When You Actually Need a Dedicated Broker

A PostgreSQL queue has hard boundaries. Know them before you hit them:

- **Sustained massive throughput**: If you process 50,000 jobs per second, PostgreSQL vacuum overhead becomes an operational burden. Redis or RabbitMQ shine here.
- **Fan-out and event streaming**: If ten microservices each need their own copy of an event stream, you want an event log like Kafka, not a competing-consumer queue.
- **Complex queue feature suites**: Fair-share scheduling across tenants, dynamic rate-limiting windows, and priority weights. Libraries like BullMQ provide these out of the box.

For Alexandryn, our throughput requirement is 400 books per import batch. Our PostgreSQL queue handles 6,000 claims per second on commodity NVMe SSDs. That is 200 times what we will ever need.

In exchange, we gained:

- 1 less daemon to supervise on macOS and Windows.
- 0 port collisions.
- 100% atomic imports through unified transactions.
- Zero dual-write hazards.
- Mathematical immunity to zombie workers through cryptographic fencing tokens.
- Deterministic 40ms unit tests.

The rule of thumb: **start with the database you already run**. Move to a dedicated broker when you can name the physical limit you are hitting, not before.
